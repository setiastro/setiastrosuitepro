Workflow Assistant

A guided, visual process planner. Build (or load) a named sequence of SASpro commands arranged into one or more parallel lanes — main, starless, stars, merge, whatever structure the processing calls for — laid out as a graph that shows where they branch and join, and step through them manually, one tool at a time. Each step opens its tool when you ask, with its captured preset pre-loaded if one was dragged in; marking a step complete adds a ✓ prefix and advances to the next. Comes with four canned workflows for common beginner paths (OSC, mono RGB, mono narrowband, Cosmic Clarity cleanup) and a compact mini-runner for executing a workflow without the full editing UI.

Workflow
Open Workflow Assistant. It opens on the graph; List View shows the same workflow as plain lists. Either pick a canned workflow from the Canned Workflows menu or build your own: drag tools from the list on the left onto any lane, add lanes for parallel branches, drop in notes and split/merge markers to document the flow. Open Step (or double-click a step) launches that tool — with any captured preset pre-loaded. Mark Complete flags the step done and bolds the next one. Save stores the workflow as a named JSON file; the active workflow is autosaved on close and restored when you reopen the dialog. Run Workflow opens the compact mini-runner, which shows the workflow without the editing controls.

Workflow Assistant complements Function Bundles rather than duplicating it. Function Bundles automate — a bundle runs its steps back-to-back, waiting on each one to complete before the next starts. Workflow Assistant guides — it shows what to do, in what order, with what settings, but each step waits for the user to actually open the tool and work it. The signature move is the multi-lane layout: lanes side by side make the parallel structure of a complex workflow (process the starless masters down one lane, the stars-only masters down another, merge at the end) visible at a glance, with split and merge markers calling out exactly where branches diverge and reconverge. This is the training-wheels tool — it lets a beginner follow a trusted recipe step by step, and lets a mentor share a workflow (with specific tool settings baked in) that a student can walk through unassisted.

1. The workflow concept

A workflow is a named, ordered sequence of steps grouped into one or more lanes. A lane is a vertical column of steps that execute in order; multiple lanes side by side represent parallel branches of the processing. Every workflow has at least one lane (named main by default) and can grow to any number of lanes as the processing demands.

A step is either an action (runs a specific SASpro command when you tell it to), a note (📝 — instruction-only, nothing to launch), a split marker (⇢ — shows where processing branches into multiple lanes), or a merge marker (⇠ — shows where branches rejoin). Action steps can carry a preset — a captured dictionary of tool settings — so “run Statistical Stretch” can become “run Statistical Stretch with these specific settings loaded in the dialog.”

Steps can also declare named inputs and outputs for lineage. These are free-form string tags (starless, stars_only, rgb_stars, palette_starless, …) that show up in the step details panel to document how data flows across the lanes. The runner doesn't enforce them — they're documentation, not routing — but a lineage you can see is far easier to follow than one you have to reconstruct from memory.

How the lanes connect is recorded as links: a step can branch into the start of another lane, or join a step part-way down another lane. Links are drawn and edited in the graph; inside a lane, the order of the steps is the connection.

The whole thing is a visible, editable, executable checklist. You open each step when you're ready, you mark it complete when the result is good, and the dialog remembers your progress and position across lanes until you reset.

2. The tool catalog

The left panel lists every SASpro command that's available as a draggable step source. Three categories of entries land here automatically:

  • Toolbar actions — any QAction on a visible toolbar that carries a command_id property. These are grouped by toolbar title (Functions, Cosmic Clarity, Tools, Geometry, Stacking, Analysis, Masks, Bundles, View, etc.) in a stable preferred order.
  • User scripts — everything in the ScriptManager registry, discovered recursively from SASpro/scripts. Scripts are shown under Scripts at the top level, with any group tag they declare rendered as a Scripts/<group> subcategory. The command id for a script is script:<script_id>.
  • Hidden toolbars are explicitly excluded (any QWidget whose windowTitle() is "Hidden" is skipped during discovery).

Each entry carries the tool's icon, display text, and status tip for hover tooltips. The search box at the top filters by text and tooltip in real time — type a few letters and the tree collapses to matching leaves (categories with no visible children also hide).

Drag any entry out of the tree onto a lane to add it as an action step, or double-click it: in the graph it goes just below the selected step, in the list at the end of the current lane. Hide Tools folds the panel away when you are following a workflow rather than building one, which gives the graph the room.

3. Lanes

Lane controls sit above the graph and the lists, and work the same in both:

  • Add Lane — prompts for a name and appends a new empty lane on the right. Names must be unique; blank names are rejected.
  • Rename Lane — asks which lane (the current one is preselected) and its new name. Every step in that lane gets its lane field updated so there's no orphaning, and links into the lane follow the new name.
  • Remove Lane — asks which lane to remove; the list shows how many steps each lane holds, so an empty lane is easy to spot. A lane with steps is removed with its steps, after a confirmation; an empty one goes straight away. A workflow always has at least one lane; the button refuses to delete the last one. In the graph, right-clicking a lane header removes or renames that lane directly.

A lane is a column of the graph. In the list view it is a vertical card with a header label and a step list below, and the lane area scrolls sideways when there are more lanes than fit.

Cross-lane selection is single-select across the whole dialog. Clicking a step in lane B clears the selection and current item in every other lane. This keeps “the current step” a single, unambiguous thing — Previous Step and Next Step walk a flat sequence across all lanes in order, and the step details panel always reflects exactly one step.

4. The graph and the list

The graph is the default view. Each lane is a column and its steps flow downward. The arrows that cross between columns are links: the places where processing branches into another lane or comes back together. A step's row is its depth in the workflow, so a branch starts just below the step it branches from, and a join sits below every step that feeds it.

The tool list is on the left, the graph in the middle, and the workflow's description, the selected step's details and the step buttons on the right. The bars between the three parts can be dragged, and the window can be maximized or moved to another monitor; its size, position and layout are remembered.

The first time it opens, the window is 1700×900, which fits a 1080p screen with room for its title bar, so it is the same size on a 1440p or 4K screen as on 1080p. Every canned workflow fits it without scrolling; the six-lane narrowband one at about 75%. On a smaller screen it takes 90% of the width and 88% of the height. A size remembered from a bigger screen is cut down to fit the screen it opens on.

List View swaps the graph for one plain list of steps per lane; Graph View swaps it back, and Ctrl+G switches between them. Both edit the same workflow and share one selection. Workflow Assistant and the mini runner each reopen in the view you last used there.

  • Branch — a link from a step to the start of another lane: that lane works on the step's result. In the narrowband workflow, each filter's Remove Stars branches into the Starless and Stars Only lanes.
  • Join — a link from a step to a particular step part-way down another lane: that step also takes the result. In SLaP Planetary, the RGB and L lanes join back into the Merge step of main.

When a link's two ends share an input/output tag, the tag is written on the arrow (Ha starless, RGB stars, …). A link can also carry a name of your own, which is written there instead.

A link into the very next row is drawn square: down from its step, across on a track of its own in the gap between the rows, and down into the step it feeds, with its name on that track just before it arrives. When several links share a gap, as the six from the narrowband workflow's Remove Stars steps do, the tracks are stacked so the links cross as little as possible: three filters each feeding two steps cross three times, the fewest any drawing can manage. Longer links are drawn as one curve.

Editing in the graph

  • Add tools — drag from the tool list, a shortcut tile or a bundle onto a lane. A bar shows where the step will land. Double-clicking a tool adds it just below the selected step. Drop onto a choice card to add an option to it, or onto the dashed + New lane column to start a lane.
  • Move steps — drag a step up or down its lane, or into another lane. A choice moves together with its options.
  • Set a step's height — drop a step in the empty space above or below it in its own lane, and it stays there. This is for joins: a step that takes results from other lanes normally sits below everything that feeds it, which can leave it at the foot of a mostly empty column. Drag it up and the steps after it in its lane, and any lane that branches from it, come up with it; links from steps that are now level with it or lower come in from the side, up the gap between two lanes when one curve would cross another step. A step never goes above the step before it in its lane, and dragging it past another step still reorders. Right-click it and choose Auto Position to put it back, or right-click empty canvas for Auto Position All Steps. The heights are saved with the workflow.
  • Branch and join — drag the small ● handle under a step and drop it on a step in another lane (join), on another lane's header or empty space (branch), or on + New lane (branch into a new lane). The hint at the bottom of the graph says what the drop will do before you let go. Links inside one lane, repeats, and links that would loop back on themselves are refused, with the reason.
  • Remove a link — click it and press Delete, or right-click it. Right-clicking a step also lists its links under Remove Link.
  • Name a link — double-click it, or right-click it and choose Name Link… (Rename Link… once it shows a tag or a name). The name is written on the arrow and in the step details. Leave it blank to show the input/output tag again. Names are saved with the workflow.
  • Step commands — right-click a step for everything the lane list offers (rename, presets, alternatives, note, inputs/outputs, remove) plus Branch Into New Lane…. Double-click or Enter opens the step; Delete removes it. Esc cancels a drag or drops the link selection.
  • Lanes — double-click a lane header to rename it. Right-click it to move the lane left or right, remove it, or add a note, choice, split or merge.

Following progress

Completed steps turn green with a ✓ badge and the current step is outlined. Previous, Next and Mark Complete move it exactly as in the list view, and the graph scrolls to keep it in sight. Ctrl+wheel zooms; F or Fit fits the workflow to the window for as long as the text stays readable, and scrolls past that; dragging the background pans. In the mini runner the graph is read-only: click to select, double-click to open, right-click for Open Step and Mark Complete.

Workflows saved before links existed describe their branches only through input/output tags. When one is loaded, SASpro derives its links from those tags once: a step that takes a tag produced in another lane gets a link from the last step there that outputs it. Saving writes the links out, and from then on they are edited directly; changing the tags later no longer moves them.

5. Adding and editing steps

Four ways to add an action step:

  • Drag a catalog entry onto any lane.
  • Double-click a catalog entry — adds it below the selected step (graph) or at the end of the current lane (list).
  • Add Selected Tool button — same as double-clicking the current catalog selection.
  • Drag a shortcut tile from SASpro's shortcut canvas onto a lane. If the tile carries a preset, the preset lands with the step (shown as a ◆ prefix on the step label and summarised in the details panel).

Dropping a Function Bundle payload onto a lane doesn't nest the bundle — it expands into one step per inner step. This matches how the shortcut canvas explodes bundles into their constituents, so a bundle built elsewhere can be used as a starter kit for a workflow.

Two ways to add a non-action step (notes, markers):

  • Add Step button — a menu with Note, Choice, Split Marker and Merge Marker. They land at the end of the current lane.
  • Right-click a lane → Add Note Step / Add Choice Group / Add Split Marker / Add Merge Marker. These land into whichever lane you right-clicked on.

Editing a step (right-click on it, or use the buttons on the right):

  • Rename… — set a custom display label (label_override). Blank restores the default (catalog text or preset-derived).
  • Edit Preset… — opens the command's bespoke preset editor via _open_preset_editor_for_command. Only available on action steps that have a command id. This edits the primary tool.
  • Add Alternative… — on an action step, pick another catalog tool to try in place of the primary one. The step stays a single checklist item. On a choice group, the same command adds a real step indented under the title.
  • Remove Alternative / Edit Alternative Preset — appear once the step has at least one alternative.
  • Edit Note — multi-line note (shown in the step details panel).
  • Edit Inputs / Outputs — comma-separated string tags.
  • Remove Step — delete it; selection stays on the same row if possible.

Reordering: drag a step within its lane or across to another lane. Qt's internal-move drag handles the heavy lifting; the workflow model is re-synced from the UI after every drop so the saved order matches what you see.

Five kinds, picked by the step's kind field:

A choice is created with Add Step → Choice. Drag a tool onto the title or onto one of its indented steps to add another alternative. Drag an indented step back out and it becomes a normal action again. Removing the title removes the actions under it as well. An action can still carry its own menu alternatives (the ▾ N badge) whether or not it sits under a choice.

Note, split, and merge steps can still carry inputs and outputs annotations — the OSC canned workflow has a split marker after Remove Stars whose two outputs (starless, stars only) feed the two lanes that follow.

Opening a non-action step shows a brief information dialog that describes what kind of marker it is. In the mini runner, opening a note step shows the step's actual note text, so the mini runner can act as a “follow this instruction” prompt even for non-action steps.

7. The step details panel

On the right, under the workflow's description, a panel shows the full details of whichever step is currently selected (in the mini runner it sits below the graph):

  • Title — the step's display label (catalog text, preset-derived label, or user override).
  • Lane — which lane the step lives in.
  • Tool status tip — for action steps, the tool's own description from its QAction.
  • Note — the step's instruction note, if any.
  • Inputs / Outputs — the named lineage tags, if any.
  • Preset — a compact summary of the first few captured settings (routing keys like family, auto_run, args, op are hidden; booleans become on/off; long strings truncate; a tail of +N more… appears when the preset has more keys than fit).
  • Alternatives — the other tools attached to this step, listed by name. The step title remains the primary tool.
  • Takes input from / Sends result to — the step's links: which steps in other lanes feed it, and which lanes or steps it hands its result to. A named link adds its name.
  • Status — Completed or Not completed.

The panel scrolls, and the bar beside it can be dragged to give it or the graph more room.

Everything is HTML-formatted inline, so the panel reads like a short field notebook entry rather than a static form.

8. Running steps and progress

Four buttons drive execution:

  • Previous Step / Next Step — walk a flat sequence of steps across all lanes in order (lane 1 top-to-bottom, then lane 2, …). The current step is bolded; selecting it also makes its lane the “current lane.”
  • Open Step — launches the current step's tool. For action steps:
    • If the step carries a preset, _preset_opener_for_command is called to open the tool seeded with those settings — the dialog pops up with every slider, dropdown, and checkbox already set.
    • If no preset (or no opener registered for that command), _find_action_by_command_id locates the QAction and triggers it directly, which usually opens the tool with its own default state.
    Double-clicking a step is a shortcut for Open Step. When the step has alternatives, Open Step (and double-click) shows a menu: the primary tool first, then each alternative. Cancelling the menu leaves the step as it is. A step with no alternatives opens its single tool directly. The step label gains a ▾ N badge, where N is the number of choices.
  • Mark Complete — flags the current step with a ✓ prefix on its label and sets its completion flag. In the mini runner, Mark Complete also advances to the next step automatically, which keeps the walkthrough moving. In the full dialog, it just marks and stays put.
  • Reset Progress — clears every step's completed flag across every lane. The workflow structure is untouched; only the progress state resets.
The runner does not wait for the tool you opened to finish. It launches the tool and returns immediately. This is deliberate — Workflow Assistant is a guided walkthrough, not an auto-runner. You open the tool, you do the work, you Mark Complete when you're happy with the result. If you want sequential auto-execution with per-step completion waits, use Function Bundles instead.

Completion state lives on each step as a Qt.UserRole + 7 flag — it's a session state, not saved into the workflow JSON. Reopening a saved workflow starts everything uncompleted; completion resets on New, on Load, on picking a canned workflow, on Clear Workflow, and on Reset Progress.

9. The mini runner

The Run Workflow button at the top right opens a Mini Workflow Dialog — a compact execution-only view of the current workflow. It shows the same graph with the same steps, but strips the editing controls (no tool list, no lane management, no edit buttons). You get the title, the graph (or the lists, with its own Graph View / List View switch), the step details panel, and five buttons: Previous, Open Step, Mark Complete, Next, Reset Progress.

The mini runner's Mark Complete automatically moves to the next step. This makes it feel more like a wizard than an editor — open the tool, do the work, hit Mark Complete, the next step is already highlighted and ready.

The mini runner can also be launched directly without opening the full editor via show_mini_workflow_dialog(main):

  • If the full dialog is open and has a non-empty workflow loaded, the mini runner just reuses that workflow and its catalog.
  • If nothing is loaded yet, a small picker appears: open the full assistant to build/edit, or launch directly into one of the canned workflows, or launch into any saved JSON file in the workflows directory.

Only one mini runner lives at a time — opening a new one closes any existing one, so you don't accumulate instances by accident.

10. Load, save, and autosave

Workflows save to the SASpro user data directory:

<user_data>/workflows/<name>.json

The user data directory is discovered via the main window's get_user_data_dir, _user_data_dir, or user_data_dir (whichever exists); if none is available, the fallback is ~/.setiastro/saspro/workflows/. The file is a UTF-8 JSON document with the full workflow definition — name, description, lanes, every step with its preset, I/O, note, kind, and label override.

Three save/load entry points:

  • Save — writes to the current workflow's name (slug-safe filename).
  • Save As… — file dialog in the workflows directory.
  • Load… — file dialog starting in the workflows directory.

Load silently migrates legacy schema v1 workflows (flat step list, no lanes) by moving every step into a single main lane. Schema v2 workflows (lanes, but no links) get their links derived from their input/output tags. Either way, the next Save writes the current v3 shape.

Autosave

Every close of the dialog, Esc included, writes the current workflow to _autosave_last_session.json in the workflows directory. Opening the dialog restores it on the next launch — but only if there's actually something to restore (non-empty step list, or a non-default name). An empty untitled autosave is treated as a no-op so you don't end up with a stale blank workflow greeting you every launch.

Autosave is deliberately silent (any exception is swallowed) so closing can never fail because of disk issues or permission problems.

11. Canned workflows

The Canned Workflows menu offers four ready-made templates. Picking one replaces the current workflow entirely.

  • Beginner OSC Workflow — 14 steps in four lanes, for one-shot color.
    • Main: Crop → ADBE → Background Neutralization → White Balance → Cosmic Clarity Sharpen → Cosmic Clarity Denoise → Remove Stars → Split
    • Starless: Statistical Stretch → Curves → Selective Color Correction → Texture and Clarity
    • Stars Only: Star Stretch
    • Combine: Add Stars, fed by both
  • Beginner Mono RGB Workflow — 16 steps in the same four lanes. The Main lane starts Crop → a note → LRGB Combination → ADBE, and everything from ADBE on is the OSC workflow. R, G and B need the same crop; Batch Crop (all open) does them at once. The note is the reminder not to add L while the image is linear: combine R, G and B only. An LRGB workflow adds L later, once the image is non-linear after Statistical Stretch.
  • Beginner Mono Narrowband Workflow — 21 steps in six lanes. Remove the SII lane if you only have Ha and OIII.
    • Ha, OIII and SII, each: Crop → ADBE → Cosmic Clarity Sharpen → Cosmic Clarity Denoise → Remove Stars. The three need the same crop; Batch Crop (all open) does them at once.
    • Starless: the three starless masters join in Perfect Palette Picker → Curves → Selective Color Correction → Texture and Clarity
    • Stars Only: the three stars-only masters join in NB→RGB Stars
    • Combine: Add Stars, fed by both
  • Cosmic Clarity Cleanup — 5 steps, one lane. A minimal pipeline for giving an already-processed image a Cosmic Clarity pass with cropping and gradient cleanup around it.

The OSC and Mono RGB workflows open with Starless and Stars Only starting at the top, beside Main, and Add Stars a row below the starless half, so the graph is no taller than Main. The links from Split run up the gaps between the lanes. These are ordinary saved step heights: right-click empty canvas for Auto Position All Steps to put the lanes back below Split.

All four canned workflows carry per-step notes describing what each step is for and why it's where it is. They're meant to be starting points — load one, rename it, add or remove steps as the data demands, and save under your own name.

12. Technical details

Internal mechanisms numbered continuing from the usage sections.

13. Data model and schema versions

A workflow is a WorkflowDefinition:

WorkflowDefinition = { "schema_version": 3, "name": "My Workflow", "description": "…", "lanes": [ "main", "starless", "stars", "merge" ], "steps": [ WorkflowStep, … ], "links": [ WorkflowLink, … ], } WorkflowLink = { "from": "<step id>", "to_lane": "stars" } # branch into a lane's start | { "from": "<step id>", "to": "<step id>" } # join a step in another lane # either can add "label": "stretched stars", the name written on the arrow WorkflowStep = { "id": "a3f1b2c4d5e6", # uuid4 hex, first 12 chars "command_id": "stretch_statistical", "note": "Stretch to non-linear.", "enabled": true, "kind": "action", # action | note | split | merge "lane": "main", "inputs": [ "aligned" ], "outputs": [ "stretched" ], "preset": { … }, # captured tool settings "label_override": "", # user-renamed display label "alternatives": [ # omitted when empty { "command_id": "curves", "preset": { }, "label_override": "" } ] }

Schema v1 was a flat step list with no lanes or I/O. The loader detects v1 by the absence of a top-level lanes key and migrates by: dropping every step into a single main lane, synthesising fresh step ids, forcing kind = "action", dropping any inputs/outputs/presets (which v1 didn't support), and tagging the result schema_version = 1 so the next Save upgrades it in place. Schema stayed at v2 for alternatives: the alternatives key is optional, so a workflow saved before this field still loads, and a step with no alternatives omits the key.

Schema v3 adds links. Links are kept consistent with the steps every time the workflow changes (normalize_workflow_links): an end on an action inside a choice moves to the choice itself, and a link is dropped when an end no longer exists, when both ends end up in the same lane, when it repeats another link, or when it would close a loop. A file without a links key gets them derived from input/output tags (derive_workflow_links); a file with an empty list keeps none. Older SASpro versions ignore the key and load the lanes as before.

14. Toolbar and script catalog discovery

The tool catalog is rebuilt every time the dialog opens via two scanners:

  • Toolbar discovery walks every QWidget child of the main window and looks for ones that have an actions() method. For each action with a command_id property, a catalog entry is created with the action's icon, text, status tip, and the toolbar's title as the category. Toolbars whose title is literally "Hidden" are skipped; separators are ignored.
  • Script discovery looks up the ScriptManager (via several candidate attribute names), calls load_registry() if the registry is empty, and iterates every registered script. Each script becomes a catalog entry under Scripts or Scripts/<group> if the script declares a group. The command id is script:<script_id>. If a matching QAction already exists on the main window (via the command_id property), its icon and tooltip are reused; otherwise a placeholder action is created.

Categories are sorted by a three-tier key: a preferred order list first (Functions, Cosmic Clarity, Tools, Geometry, Stacking, Analysis, Masks, What's In My…, Bundles, View, Scripts), then Scripts/* subcategories alphabetically, then everything else alphabetically. The search box filters by matching both the action text and its tooltip, case-insensitive.

15. MIME payload types and function-bundle expansion

The lane list accepts two MIME formats:

  • application/x-saspro-workflow-command (WORKFLOW_MIME) — a bare UTF-8 command id, dragged from the catalog tree. Lands as an action step with an empty preset.
  • application/x-saspro-command (MIME_CMD) — the standard SASpro shortcut payload, dragged from the shortcut canvas or from Function Bundle chips. Contains a dict with command_id and optional preset.

When the MIME_CMD payload has command_id == "function_bundle", the drop handler walks the inner steps array and adds one action step per element, each with its own command id and preset. This mirrors the shortcut canvas's own bundle-expansion behaviour (add_shortcut_from_payload / _add_shortcuts_from_steps) so the UX is consistent across drop targets.

16. Cross-lane single-selection coordination

Qt's QListWidget maintains independent selection state per widget — by default, selecting an item in lane B wouldn't clear the selection in lane A. Workflow Assistant forces single-selection across all lanes with a cross-list coordinator.

When any lane's selection changes, _on_any_step_selected walks every other lane list and clears its selection, current row, and current item — signals blocked during the clear so no recursive callbacks fire. It also clears the selection model's own cached selection and current index to be sure Qt doesn't restore the old state on a repaint.

The “current lane” is then set to the lane whose selection just changed, and both the step details panel and the lane visual refresh (bolding the current step, applying ✓ prefixes) run against the new unique selection.

17. Preset-aware label derivation

Dragging a preset-bearing shortcut tile into a workflow captures both the command id and the preset. Several commands dispatch to different underlying tools based on preset content — rcastro runs BXT/SXT/NXT depending on preset["product"]; cosmic_clarity runs Sharpen/Denoise/Both/Super-Res based on preset["mode"]; syqontools picks between Prism Denoise / Parallax / Starless on preset["family"]. A plain “RC-Astro” step label would be useless in those cases.

_derive_step_label handles these cases explicitly:

rcastro + product=bxt → "BlurXTerminator" cosmic_clarity + mode=sharpen → "Cosmic Clarity — Sharpen" syqontools + family=denoise → "SyQon — Prism Denoise" fx + effect=soft_glow → "FX — Soft Glow" remove_stars + tool=starnet → "Remove Stars — StarNet"

The derivation runs when a preset-bearing step is added and the drop didn't come with its own explicit name. The result goes into the step's label_override, so it survives save/load and shows up in both the main dialog and the mini runner. A user Rename still wins — manual overrides are preserved over derived ones.

18. Preset-seeded step opener

When Open Step runs on a preset-bearing action step, the runner tries _preset_opener_for_command(command_id) from setiastro.saspro.shortcuts first. This returns a callable (or None) that knows how to open the specific tool with the preset pre-loaded — typically by constructing the dialog, iterating the preset keys, and setting the matching widget state directly.

The canned Cosmic Clarity steps carry only {"mode": "sharpen"} or {"mode": "denoise"}. A preset that names only the mode sets only the mode: the dialog keeps your own strengths, GPU and temporary-stretch settings. A preset dragged in from the tool carries every setting and applies them all.

If a preset-bearing opener is registered, it's called with (main_window, preset_dict). If no opener is registered (or the import fails), the runner falls back to the plain-action path: find the QAction by command id and trigger() it, which opens the tool with its own default state. The user then has to re-apply their saved settings manually — the preset is still visible in the step details panel so they can read it off.

19. Autosave and session restore

Autosave triggers on closeEvent of the dialog, and on reject because Esc does not send one — the current workflow is synced from the UI, name and description are refreshed from the editable fields, and the whole thing serialises to _autosave_last_session.json in the workflows directory. The autosave is wrapped in a bare try/except that swallows every exception; closing the dialog must never fail because of a save issue.

Session restore runs after dialog construction, in _restore_autosaved_session. The autosave file is read, parsed with WorkflowDefinition.from_dict, and the result is loaded only if it has substantive content — either a non-empty steps list or a non-default name. An untitled autosave with zero steps is treated as nothing to restore, which prevents a stale blank workflow from reappearing every launch.

The autosave file lives alongside named user workflows in the workflows directory but prefixed with an underscore to sort it out of the way of the Load dialog's typical browse order.

Workflow Assistant is a workflow / mentoring tool for SetiAstro Suite Pro by Franklin Marek. It builds on standard SASpro machinery: the toolbar & QAction system (every action auto-discoverable by command_id property), the ScriptManager registry (recursive script discovery), the SASpro shortcut MIME protocol (MIME_CMD) and the shortcut-canvas's preset-opener dispatch (_preset_opener_for_command, _open_preset_editor_for_command). The canned workflows are curated beginner recipes; the multi-lane visual layout, split/merge markers, and I/O lineage annotations are new design work for this tool. There are no external algorithmic references — this tool orchestrates SASpro's existing commands rather than introducing new image-processing primitives. Qt and PyQt6 provide the UI framework, drag-and-drop infrastructure, and JSON serialisation.
