Workflow Assistant

A guided, visual process planner. Build (or load) a named sequence of SASpro commands arranged into one or more parallel lanes — main, starless, stars, merge, whatever structure the processing calls for — and step through them manually, one tool at a time. Each step opens its tool when you ask, with its captured preset pre-loaded if one was dragged in; marking a step complete adds a ✓ prefix and advances to the next. Comes with four canned workflows for common beginner paths (OSC, mono RGB, mono narrowband, Cosmic Clarity cleanup) and a compact mini-runner for executing a workflow without the full editing UI.

Workflow
Open Workflow Assistant. Either pick a canned workflow from the Add Canned Workflow menu or build your own: drag tools from the catalog on the left into any lane on the right, add lanes for parallel branches, drop in notes and split/merge markers to document the flow. Open Step (or double-click a step) launches that tool — with any captured preset pre-loaded. Mark Complete flags the step done and bolds the next one. Save stores the workflow as a named JSON file; the active workflow is autosaved on close and restored when you reopen the dialog. Run Workflow opens the compact mini-runner that shows the lanes without the editing controls.

Workflow Assistant complements Function Bundles rather than duplicating it. Function Bundles automate — a bundle runs its steps back-to-back, waiting on each one to complete before the next starts. Workflow Assistant guides — it shows what to do, in what order, with what settings, but each step waits for the user to actually open the tool and work it. The signature move is the multi-lane layout: horizontal lanes make the parallel structure of a complex workflow (process the starless masters down one lane, the stars-only masters down another, merge at the end) visible at a glance, with split and merge markers calling out exactly where branches diverge and reconverge. This is the training-wheels tool — it lets a beginner follow a trusted recipe step by step, and lets a mentor share a workflow (with specific tool settings baked in) that a student can walk through unassisted.

1. The workflow concept

A workflow is a named, ordered sequence of steps grouped into one or more lanes. A lane is a vertical column of steps that execute in order; multiple lanes side by side represent parallel branches of the processing. Every workflow has at least one lane (named main by default) and can grow to any number of lanes as the processing demands.

A step is either an action (runs a specific SASpro command when you tell it to), a note (📝 — instruction-only, nothing to launch), a split marker (⇢ — shows where processing branches into multiple lanes), or a merge marker (⇠ — shows where branches rejoin). Action steps can carry a preset — a captured dictionary of tool settings — so “run Statistical Stretch” can become “run Statistical Stretch with these specific settings loaded in the dialog.”

Steps can also declare named inputs and outputs for lineage. These are free-form string tags (starless, stars_only, rgb_stars, palette_starless, …) that show up in the step details panel to document how data flows across the lanes. The runner doesn't enforce them — they're documentation, not routing — but a lineage you can see is far easier to follow than one you have to reconstruct from memory.

The whole thing is a visible, editable, executable checklist. You open each step when you're ready, you mark it complete when the result is good, and the dialog remembers your progress and position across lanes until you reset.

2. The tool catalog

The left panel lists every SASpro command that's available as a draggable step source. Three categories of entries land here automatically:

  • Toolbar actions — any QAction on a visible toolbar that carries a command_id property. These are grouped by toolbar title (Functions, Cosmic Clarity, Tools, Geometry, Star Stuff, Masks, Bundles, View, etc.) in a stable preferred order.
  • User scripts — everything in the ScriptManager registry, discovered recursively from SASpro/scripts. Scripts are shown under Scripts at the top level, with any group tag they declare rendered as a Scripts/<group> subcategory. The command id for a script is script:<script_id>.
  • Hidden toolbars are explicitly excluded (any QWidget whose windowTitle() is "Hidden" is skipped during discovery).

Each entry carries the tool's icon, display text, and status tip for hover tooltips. The search box at the top filters by text and tooltip in real time — type a few letters and the tree collapses to matching leaves (categories with no visible children also hide).

Drag any entry out of the tree onto a lane list to add it as an action step; double-click a leaf to add it to the currently active lane without having to drag.

3. Lanes

Lane controls sit above the lane cards:

  • Add Lane — prompts for a name and appends a new empty lane on the right. Names must be unique; blank names are rejected.
  • Rename Lane — renames the current lane; every step currently in that lane gets its lane field updated so there's no orphaning.
  • Remove Lane — drops the current lane and every step in it, after a confirmation. A workflow always has at least one lane; the button refuses to delete the last one.

Each lane is a vertical card with a header label and a step list below. The lane area scrolls horizontally when there's more lane than fits, so a four-lane narrowband workflow sits comfortably in a 1400 px dialog.

Cross-lane selection is single-select across the whole dialog. Clicking a step in lane B clears the selection and current item in every other lane. This keeps “the current step” a single, unambiguous thing — Previous Step and Next Step walk a flat sequence across all lanes in order, and the step details panel always reflects exactly one step.

4. Adding and editing steps

Four ways to add an action step:

  • Drag a catalog entry onto any lane list.
  • Double-click a catalog entry — adds to the current lane (or main if nothing is selected).
  • Add Selected Tool button — same as double-clicking the current catalog selection.
  • Drag a shortcut tile from SASpro's shortcut canvas onto a lane. If the tile carries a preset, the preset lands with the step (shown as a ◆ prefix on the step label and summarised in the details panel).

Dropping a Function Bundle payload onto a lane doesn't nest the bundle — it expands into one step per inner step. This matches how the shortcut canvas explodes bundles into their constituents, so a bundle built elsewhere can be used as a starter kit for a workflow.

Three ways to add a non-action step (notes, markers):

  • Add Note / Add Split / Add Merge buttons.
  • Right-click a lane → Add Note Step / Add Split Marker / Add Merge Marker. These land into whichever lane you right-clicked on.
  • Add Note at the top-level buttons appends to the current lane.

Editing a step (right-click on it, or use the toolbar buttons):

  • Rename… — set a custom display label (label_override). Blank restores the default (catalog text or preset-derived).
  • Edit Preset… — opens the command's bespoke preset editor via _open_preset_editor_for_command. Only available on action steps that have a command id.
  • Edit Note — multi-line note (shown in the step details panel).
  • Edit Inputs / Outputs — comma-separated string tags.
  • Remove Step — delete it; selection stays on the same row if possible.

Reordering: drag a step within its lane or across to another lane. Qt's internal-move drag handles the heavy lifting; the workflow model is re-synced from the UI after every drop so the saved order matches what you see.

5. Step kinds

Four kinds, picked by the step's kind field:

KindPrefixPurposeOpens a tool?
action(none, or ◆ with preset)Runs a specific SASpro command when opened.Yes
note📝Instruction-only step. Carries a note describing what the user should do next.No
split⇢Visual branch marker. Documents where processing diverges into multiple lanes.No
merge⇠Visual merge marker. Documents where multiple lanes come back together.No

Note, split, and merge steps can still carry inputs and outputs annotations — the narrowband canned workflow uses split and merge markers to call out the branch and the rejoin, with named outputs on the split (starless, stars_only) and named inputs on the merge (starless_final, stars_final).

Opening a non-action step shows a brief information dialog that describes what kind of marker it is. In the mini runner, opening a note step shows the step's actual note text, so the mini runner can act as a “follow this instruction” prompt even for non-action steps.

6. The step details panel

Below the lanes sits a panel that shows the full details of whichever step is currently selected:

  • Title — the step's display label (catalog text, preset-derived label, or user override).
  • Lane — which lane the step lives in.
  • Tool status tip — for action steps, the tool's own description from its QAction.
  • Note — the step's instruction note, if any.
  • Inputs / Outputs — the named lineage tags, if any.
  • Preset — a compact summary of the first few captured settings (routing keys like family, auto_run, args, op are hidden; booleans become on/off; long strings truncate; a tail of +N more… appears when the preset has more keys than fit).
  • Status — Completed or Not completed.

Everything is HTML-formatted inline, so the panel reads like a short field notebook entry rather than a static form.

7. Running steps and progress

Four buttons drive execution:

  • Previous Step / Next Step — walk a flat sequence of steps across all lanes in order (lane 1 top-to-bottom, then lane 2, …). The current step is bolded; selecting it also makes its lane the “current lane.”
  • Open Step — launches the current step's tool. For action steps:
    • If the step carries a preset, _preset_opener_for_command is called to open the tool seeded with those settings — the dialog pops up with every slider, dropdown, and checkbox already set.
    • If no preset (or no opener registered for that command), _find_action_by_command_id locates the QAction and triggers it directly, which usually opens the tool with its own default state.
    Double-clicking a step is a shortcut for Open Step.
  • Mark Complete — flags the current step with a ✓ prefix on its label and sets its completion flag. In the mini runner, Mark Complete also advances to the next step automatically, which keeps the walkthrough moving. In the full dialog, it just marks and stays put.
  • Reset Progress — clears every step's completed flag across every lane. The workflow structure is untouched; only the progress state resets.
The runner does not wait for the tool you opened to finish. It launches the tool and returns immediately. This is deliberate — Workflow Assistant is a guided walkthrough, not an auto-runner. You open the tool, you do the work, you Mark Complete when you're happy with the result. If you want sequential auto-execution with per-step completion waits, use Function Bundles instead.

Completion state lives on each step as a Qt.UserRole + 7 flag — it's a session state, not saved into the workflow JSON. Reopening a saved workflow starts everything uncompleted; completion resets on New Workflow, on Load, on Clear Workflow, and on Reset Progress.

8. The mini runner

The Run Workflow button at the bottom of the dialog opens a Mini Workflow Dialog — a compact execution-only view of the current workflow. It shows the same lanes with the same steps, but strips the editing controls (no catalog panel, no lane management, no edit buttons). You get a title bar, the lanes themselves, the step details panel, and five buttons: Previous, Open Step, Mark Complete, Next, Reset Progress.

The mini runner's Mark Complete automatically moves to the next step. This makes it feel more like a wizard than an editor — open the tool, do the work, hit Mark Complete, the next step is already highlighted and ready.

The mini runner can also be launched directly without opening the full editor via show_mini_workflow_dialog(main):

  • If the full dialog is open and has a non-empty workflow loaded, the mini runner just reuses that workflow and its catalog.
  • If nothing is loaded yet, a small picker appears: open the full assistant to build/edit, or launch directly into one of the canned workflows, or launch into any saved JSON file in the workflows directory.

Only one mini runner lives at a time — opening a new one closes any existing one, so you don't accumulate instances by accident.

9. Load, save, and autosave

Workflows save to the SASpro user data directory:

<user_data>/workflows/<name>.json

The user data directory is discovered via the main window's get_user_data_dir, _user_data_dir, or user_data_dir (whichever exists); if none is available, the fallback is ~/.setiastro/saspro/workflows/. The file is a UTF-8 JSON document with the full workflow definition — name, description, lanes, every step with its preset, I/O, note, kind, and label override.

Three save/load entry points:

  • Save — writes to the current workflow's name (slug-safe filename).
  • Save As… — file dialog in the workflows directory.
  • Load… — file dialog starting in the workflows directory.

Load silently migrates legacy schema v1 workflows (flat step list, no lanes) into the current v2 shape by moving every step into a single main lane. The migrated workflow saves back in v2 shape the next time you hit Save.

Autosave

Every close of the dialog writes the current workflow to _autosave_last_session.json in the workflows directory. Opening the dialog restores it on the next launch — but only if there's actually something to restore (non-empty step list, or a non-default name). An empty untitled autosave is treated as a no-op so you don't end up with a stale blank workflow greeting you every launch.

Autosave is deliberately silent (any exception is swallowed) so closing can never fail because of disk issues or permission problems.

10. Canned workflows

The Add Canned Workflow dropdown offers four ready-made templates. Picking one replaces the current workflow entirely.

  • Beginner OSC Workflow — 10 steps, one lane. Crop → Pedestal → ABE → Background Neutral → White Balance → Cosmic Clarity → Statistical Stretch → Curves → CLAHE → Save As. Simple linear path for one-shot colour cameras.
  • Beginner Mono RGB Workflow — 11 steps, one lane. Crop → Pedestal → Linear Fit → RGB Combine → Background Neutral → White Balance → Cosmic Clarity → Statistical Stretch → Curves → CLAHE → Save As. Mono-RGB channel combination path.
  • Beginner Mono Narrowband Workflow — 17 steps across four lanes (main, starless, stars, merge). The workflow splits after Remove Stars, processes starless and stars-only masters down separate lanes, and merges with Add Stars. This is the canonical multi-lane example — it shows how split/merge markers combine with lane layout to make a complex pipeline visually obvious.
  • Cosmic Clarity Cleanup — 5 steps, one lane. A minimal pipeline for giving an already-processed image a Cosmic Clarity pass with cropping and gradient cleanup around it.

All four canned workflows carry per-step notes describing what each step is for and why it's where it is. They're meant to be starting points — load one, rename it, add or remove steps as the data demands, and save under your own name.

11. Technical details

Internal mechanisms numbered continuing from the usage sections.

12. Data model and schema versions

A workflow is a WorkflowDefinition:

WorkflowDefinition = { "schema_version": 2, "name": "My Workflow", "description": "…", "lanes": [ "main", "starless", "stars", "merge" ], "steps": [ WorkflowStep, … ], } WorkflowStep = { "id": "a3f1b2c4d5e6", # uuid4 hex, first 12 chars "command_id": "stretch_statistical", "note": "Stretch to non-linear.", "enabled": true, "kind": "action", # action | note | split | merge "lane": "main", "inputs": [ "aligned" ], "outputs": [ "stretched" ], "preset": { … }, # captured tool settings "label_override": "", # user-renamed display label }

Schema v1 was a flat step list with no lanes or I/O. The loader detects v1 by the absence of a top-level lanes key and migrates by: dropping every step into a single main lane, synthesising fresh step ids, forcing kind = "action", dropping any inputs/outputs/presets (which v1 didn't support), and tagging the result schema_version = 1 so the next Save upgrades it in place.

13. Toolbar and script catalog discovery

The tool catalog is rebuilt every time the dialog opens via two scanners:

  • Toolbar discovery walks every QWidget child of the main window and looks for ones that have an actions() method. For each action with a command_id property, a catalog entry is created with the action's icon, text, status tip, and the toolbar's title as the category. Toolbars whose title is literally "Hidden" are skipped; separators are ignored.
  • Script discovery looks up the ScriptManager (via several candidate attribute names), calls load_registry() if the registry is empty, and iterates every registered script. Each script becomes a catalog entry under Scripts or Scripts/<group> if the script declares a group. The command id is script:<script_id>. If a matching QAction already exists on the main window (via the command_id property), its icon and tooltip are reused; otherwise a placeholder action is created.

Categories are sorted by a three-tier key: a preferred order list first (Functions, Cosmic Clarity, Tools, Geometry, Star Stuff, Masks, What's In My…, Bundles, View, Scripts), then Scripts/* subcategories alphabetically, then everything else alphabetically. The search box filters by matching both the action text and its tooltip, case-insensitive.

14. MIME payload types and function-bundle expansion

The lane list accepts two MIME formats:

  • application/x-saspro-workflow-command (WORKFLOW_MIME) — a bare UTF-8 command id, dragged from the catalog tree. Lands as an action step with an empty preset.
  • application/x-saspro-command (MIME_CMD) — the standard SASpro shortcut payload, dragged from the shortcut canvas or from Function Bundle chips. Contains a dict with command_id and optional preset.

When the MIME_CMD payload has command_id == "function_bundle", the drop handler walks the inner steps array and adds one action step per element, each with its own command id and preset. This mirrors the shortcut canvas's own bundle-expansion behaviour (add_shortcut_from_payload / _add_shortcuts_from_steps) so the UX is consistent across drop targets.

15. Cross-lane single-selection coordination

Qt's QListWidget maintains independent selection state per widget — by default, selecting an item in lane B wouldn't clear the selection in lane A. Workflow Assistant forces single-selection across all lanes with a cross-list coordinator.

When any lane's selection changes, _on_any_step_selected walks every other lane list and clears its selection, current row, and current item — signals blocked during the clear so no recursive callbacks fire. It also clears the selection model's own cached selection and current index to be sure Qt doesn't restore the old state on a repaint.

The “current lane” is then set to the lane whose selection just changed, and both the step details panel and the lane visual refresh (bolding the current step, applying ✓ prefixes) run against the new unique selection.

16. Preset-aware label derivation

Dragging a preset-bearing shortcut tile into a workflow captures both the command id and the preset. Several commands dispatch to different underlying tools based on preset content — rcastro runs BXT/SXT/NXT depending on preset["product"]; cosmic_clarity runs Sharpen/Denoise/Both/Super-Res based on preset["mode"]; syqontools picks between Prism Denoise / Parallax / Starless on preset["family"]. A plain “RC-Astro” step label would be useless in those cases.

_derive_step_label handles these cases explicitly:

rcastro + product=bxt → "BlurXTerminator" cosmic_clarity + mode=sharpen → "Cosmic Clarity — Sharpen" syqontools + family=denoise → "SyQon — Prism Denoise" fx + effect=soft_glow → "FX — Soft Glow" remove_stars + tool=starnet → "Remove Stars — StarNet"

The derivation runs when a preset-bearing step is added and the drop didn't come with its own explicit name. The result goes into the step's label_override, so it survives save/load and shows up in both the main dialog and the mini runner. A user Rename still wins — manual overrides are preserved over derived ones.

17. Preset-seeded step opener

When Open Step runs on a preset-bearing action step, the runner tries _preset_opener_for_command(command_id) from setiastro.saspro.shortcuts first. This returns a callable (or None) that knows how to open the specific tool with the preset pre-loaded — typically by constructing the dialog, iterating the preset keys, and setting the matching widget state directly.

If a preset-bearing opener is registered, it's called with (main_window, preset_dict). If no opener is registered (or the import fails), the runner falls back to the plain-action path: find the QAction by command id and trigger() it, which opens the tool with its own default state. The user then has to re-apply their saved settings manually — the preset is still visible in the step details panel so they can read it off.

18. Autosave and session restore

Autosave triggers on closeEvent of the dialog — the current workflow is synced from the UI, name and description are refreshed from the editable fields, and the whole thing serialises to _autosave_last_session.json in the workflows directory. The autosave is wrapped in a bare try/except that swallows every exception; closing the dialog must never fail because of a save issue.

Session restore runs after dialog construction, in _restore_autosaved_session. The autosave file is read, parsed with WorkflowDefinition.from_dict, and the result is loaded only if it has substantive content — either a non-empty steps list or a non-default name. An untitled autosave with zero steps is treated as nothing to restore, which prevents a stale blank workflow from reappearing every launch.

The autosave file lives alongside named user workflows in the workflows directory but prefixed with an underscore to sort it out of the way of the Load dialog's typical browse order.
