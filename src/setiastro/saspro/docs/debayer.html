Debayer

Converts a single-channel CFA (colour-filter-array) mosaic into a 3-channel RGB image. Supports both standard 2×2 Bayer mosaics (RGGB, BGGR, GRBG, GBRG) via SASpro's Numba-accelerated kernels and Fujifilm X-Trans 6×6 mosaics via rawpy / LibRaw. The dialog auto-detects the CFA family and the Bayer phase from the header, falls back to the camera model, falls back to rawpy's ground truth, and ultimately falls back to a brute-force colour-difference-gradient score if the metadata is silent. ROWORDER handling (bottom-up FITS from NINA and similar) is built in and applied symmetrically so the output orientation always matches the input.

Original work for SetiAstro Suite Pro. The underlying demosaic algorithms (VNG, Hamilton–Adams edge-aware, bilinear, AHD, DHT) are classical and credited below — SASpro's job is to pick the right one, pass it clean inputs, and get the orientation right. The dispatch and detection machinery, the orientation invariant, and the headless entry point are new work by Franklin Marek. SASpro-exclusive content: the dual-family CFA dispatcher that routes Bayer mosaics to the Numba kernel chain and X-Trans mosaics to a rawpy decode path from the same dialog with no user flag required; the four-tier CFA-family detector that walks header-blob substring match (X-TRANS / XTRANS / FUJIFILM X-TRANS) → direct Bayer-token presence (RGGB / BGGR / GRBG / GBRG / BAYER) → camera-model hint against a 15-body Fujifilm X-Trans list (X-T1…X-T5, X-E2…X-E3, X-Pro1…X-Pro3, X-H1 / X-H2S, X-S10 / X-S20, X100, X70, X30) → rawpy ground truth from the source RAW when a path is reachable; Workflow
Open Debayer on a single-channel mosaic view. Confirm the detected pattern (shown next to the dropdown, with XBAYROFF, YBAYROFF, and ROWORDER from the header) or pick one explicitly. Pick a method — VNG is the default and the usual best choice; Edge-aware trades a bit of smoothness for sharper edges; Bilinear is fastest; Strict CFA splits channels without interpolation (half the resolution per axis, useful as a quick preview). X-Trans data is routed to rawpy automatically; pick AHD or DHT. OK runs the demosaic, pushes the RGB back into the same document (with undo if the doc supports it), and refreshes just that view without switching focus.

The signature move is the auto-detect dispatch chain. For a correctly-tagged file (BAYERPAT = RGGB in the header), opening Debayer and hitting OK just works. For an untagged FITS that came from a bottom-up NINA pipeline, SASpro picks up ROWORDER = BOTTOM-UP, flips the mosaic to top-down, debayers under the header-declared pattern (or scores the four candidates if the header has nothing), flips the RGB back, and lands the result in the right orientation. For a Fujifilm RAF opened and converted to FITS, the dialog spots the X-Trans fingerprint in the metadata, hunts for the original RAF next to the FITS if the stored path is stale, and hands the decode off to LibRaw via rawpy with AHD or DHT — because X-Trans's non-repeating 6×6 pattern can't be handled by the Numba Bayer kernels. One dialog, one OK button, four demosaic algorithms, two CFA families, and the orientation always matches input.

1. What Debayer accepts

The dialog opens on the active view and requires a single-channel 2D mosaic as input. The early checks reject anything else:

  • If the active image is already 3-channel (RGB), the dialog shows a “3 channels already” information message and closes — nothing to demosaic.
  • If the active image isn't 2D (e.g. a stack, a video, a weird N-D array), it shows a warning and closes.
  • If no view is active, the dialog refuses to open from the start.

Accepted input dtypes: any integer (uint8, uint16, uint32, …) or any float. Integer inputs are scaled by their dtype's native maximum (iinfo.max) into [0, 1]. Float inputs stay as-is unless they look like unnormalised 16-bit ADU values (max > 256), in which case they're divided by 65535. See the Technical details section on normalisation for why the threshold is 256 and not 1.

2. Pattern selection

The top group box lets you pick which Bayer phase the mosaic uses:

  • Auto (from header) — default. Uses whatever pattern the dialog detected on open, shown next to the dropdown as e.g. Detected: RGGB (XBAYROFF=0, YBAYROFF=0, ROWORDER=TOP-DOWN). If the header had no pattern, Auto triggers the brute-force scoring fallback on OK.
  • RGGB / BGGR / GRBG / GBRG — explicit override. The four possible 2×2 Bayer phases.

A Bayer phase is just the colour at the top-left of the 2×2 repeating tile. The four patterns correspond to the four possible rotations:

Pattern(0, 0)(0, 1)(1, 0)(1, 1)
RGGBRGGB
BGGRBGGR
GRBGGRBG
GBRGGBRG

The pattern dropdown is disabled when the dialog has detected X-Trans data — X-Trans doesn't have a 2×2 phase; the whole thing is handed off to rawpy.

3. Bayer methods

Four methods for standard Bayer data, all running through SASpro's Numba-accelerated debayer_fits_fast:

  • VNG (Variable Number of Gradients) — the default. Chang, Cheung & Pollard 1999. Computes eight directional gradients around each pixel, selects the ones below a threshold, and interpolates from only those directions. Produces excellent results on both smooth and high-detail regions; the usual best choice for astronomical data.
  • Edge-aware (Numba) — a Hamilton–Adams-style gradient-informed interpolation. Chooses the interpolation direction based on local gradient strength, so it preserves edges better than bilinear while being faster than VNG.
  • Bilinear (Numba) — simple linear interpolation. Fastest; produces slightly softer output than VNG or edge-aware. Useful when demosaicing is on the critical path of a long batch.
  • Strict CFA (no interpolation) — just splits the mosaic into its three channels at native CFA resolution. The output is half the resolution on each axis (one R, two Gs averaged, and one B per 2×2 block). Useful as an instant preview, or as the input to a subsequent super-resolution step that expects pre-split channels.
For most deep-sky work, VNG is the right default. Switch to Edge-aware when you want tighter edges around high-contrast features (bright stars, galaxy cores); switch to Bilinear only when speed matters more than quality.

4. X-Trans path

Fujifilm's X-Trans CFA is a 6×6 repeating pattern — much more complex than Bayer's 2×2 and specifically designed to break moiré without an optical low-pass filter. The Numba Bayer kernels can't handle it; demosaicing goes to rawpy (the Python wrapper around LibRaw) with two selectable algorithms:

  • AHD (rawpy) — Adaptive Homogeneity-Directed demosaicing (Hirakawa & Parks 2005). The default X-Trans algorithm; interpolates in whichever direction has the most homogeneous result after conversion to CIELab. Good general-purpose quality.
  • DHT (rawpy) — An alternative LibRaw implementation (Petrusevich). Different trade-offs; sometimes cleaner on fine periodic detail.

X-Trans demosaicing requires access to the original RAW file, not the derived FITS. The dialog finds it through a multi-source search:

1. metadata["raw_source_path"] 2. header cards: RAW_PATH, RAWFILE, ORIGFILE, ORIGINAL, ORIGPATH, RAWORIG, SOURCE, SRCFILE 3. doc.file_path / doc.path / metadata["file_path"] 4. sibling file scan: same stem, in the same folder, with any of .raf / .raw / .rw2 / .arw / .nef / .cr2 / .cr3 / .dng / .orf / .pef extensions

If every source fails, the dialog shows a message explaining that the X-Trans original couldn't be found and suggesting three fixes: open the RAF directly, embed a RAW_PATH card in the header, or place the RAW next to the file.

rawpy runs with use_camera_wb=True (camera's shot white balance), no_auto_bright=True (no auto-brightening), gamma (1.0, 1.0) (linear output), 16-bit output, FBDD noise reduction off, and highlights clipped. The float32 RGB result in [0, 1] is handed back to the apply layer the same way the Numba path's output is.

5. ROWORDER handling

FITS files have no universal convention for which pixel is first. NINA and some other acquisition tools write ROWORDER = BOTTOM-UP, meaning row 0 of the on-disk array is the bottom of the sensor, not the top. The Bayer pattern header card describes the sensor's actual CFA layout — which is a top-down fact — so a bottom-up file has its mosaic rows in the opposite order from what the Bayer phase declaration implies.

The fix is a once-only flip:

I_{\mathrm{td}} = flipud(I_{\mathrm{bu}}) # flip the mosaic to top-down R_{\mathrm{td}} = debayer(I_{\mathrm{td}}, p) # debayer with header-declared pattern R_{\mathrm{bu}} = flipud(R_{\mathrm{td}}) # flip the RGB back for display

The input flip ensures the Bayer phase matches the on-disk pixel grid; the output flip restores the orientation the user expects to see.

The critical invariant is that this flip and the pattern-detection logic in bayer_utils are mutually exclusive — pattern detection does not also bump the Y offset by the height parity, so a BOTTOM-UP file is never corrected twice. If the detector and the flip both tried to compensate for the row order, they'd stack into the wrong pattern (effectively swapping R ↔ B or shifting the phase). The invariant is enforced by the bayer_utils module and must be preserved by anything else that calls into this path.

6. Applying the result

Once the RGB result is ready (from either the Numba worker or the rawpy path), it's pushed back to the source document — never to “the active view” by position. The apply layer walks a two-tier preference:

  • Preferred: if the document exposes apply_edit(image, metadata, step_name), call it. This gives the user a proper undoable edit with a named step (Debayer (RGGB), Debayer (X-Trans/AHD), etc.), participates in the undo stack, and triggers any downstream notifications the doc model emits. A one-arg legacy fallback apply_edit(image) is also tried if the full signature isn't accepted.
  • Fallback: direct mutation of doc.image plus a metadata patch (is_mono = False, bit_depth defaults to 32-bit float), followed by an explicit view refresh.

View refresh is done by locating the MDI subwindow bound to the specific document (not the active one) and calling its refresh_pixmap_from_document, refresh_view, or update_from_doc hook if present, falling back to a plain update() on both the view and the subwindow. The user's current window focus doesn't change.

7. Headless and script entry points

Two headless entry points for scripts, presets, and the Replay Last Action system:

  • debayer_array(mono, pattern, roworder, method, cfa_drizzle) — pure function. Takes a mosaic array, returns an RGB array. No doc, no Qt, no side effects. This is the single source of truth for the flip-in / debayer / flip-out orientation handling — the interactive dialog, the preset runner, and the stacking pipeline all go through it, so the same mosaic always produces the same RGB regardless of which entry point was used.
  • apply_debayer_preset_to_doc(dm, doc, preset) — doc-aware version. Takes a preset dict ({"pattern": "auto|RGGB|…", "method": "auto|vng|edge|…|AHD|DHT"}), handles the CFA-family dispatch, runs the appropriate engine, applies the result to the given doc, and returns (used_pattern, rgb_array).

The command runner run_debayer_via_preset(main, preset, doc=None) wires both of these into SASpro's command system. It registers the invocation with the Replay Last Action buffer so Ctrl+Shift+R can repeat the same debayer with the same settings on the next image. If no explicit doc is passed, the active doc is used.

A typical preset for scripting:

preset = { "pattern": "auto", # auto | RGGB | BGGR | GRBG | GBRG "method": "vng", # auto | vng | edge | bilinear | strict_cfa # (or AHD / DHT for X-Trans) } run_debayer_via_preset(main, preset)

9. CFA family auto-detection

Deciding whether a mosaic is Bayer or X-Trans runs a four-tier chain, stopping at the first positive answer:

  1. Header blob substring match — serialise both the header object and the metadata dict to strings, uppercase, and search for X-TRANS / XTRANS / FUJIFILM X-TRANS. If any hit, return XTRANS. Otherwise search for BAYER / RGGB / BGGR / GRBG / GBRG; any hit returns BAYER.
  2. Camera model hint — if MAKE contains FUJIFILM and MODEL matches one of 15 known X-Trans bodies (X-T1…X-T5, X-E2 / X-E2S / X-E3, X-Pro1…X-Pro3, X-H1 / X-H2S, X-S10 / X-S20, X100, X70, X30), return XTRANS.
  3. rawpy ground truth — if a RAW source path is reachable, open it with rawpy and check: non-None xtrans_pattern → XTRANS; a 2×2 raw_pattern → BAYER.
  4. No signal — return None, which the dialog treats as “Bayer, no header pattern.” The brute-force scorer then runs on OK.

The camera-model list is conservative — it only matches bodies where X-Trans is known to be used, not every Fuji camera (the X100 / X70 / X30 are included because specific models in those lines are X-Trans too, but recent entries in those lines might ship a Bayer sensor and would need the rawpy check to confirm).

10. Bayer phase auto-detection

Within the Bayer family, picking which of the four 2×2 phases to use runs a parallel four-tier chain:

  1. Explicit header card — a BAYERPAT / XBAYROFF+YBAYROFF / similar card is read and normalised to one of the four canonical tokens (RGGB / BGGR / GRBG / GBRG).
  2. rawpy's raw_pattern — if a RAW path is reachable, rawpy reports the actual sensor CFA.
  3. Brute-force scoring — see §11.
  4. Fallback — if everything fails, RGGB. (This is the most common pattern on modern CMOS; being wrong just means the user sees R↔B swap or a chequerboard moiré and picks the right one explicitly.)

11. The scoring heuristic

When no header pattern and no rawpy source exist, SASpro picks the Bayer phase by actually debayering under each of the four candidates and scoring the result. The score penalises Sobel gradient energy in the colour-difference planes:

G_{x} = S_{x} \ast I,\quad G_{y} = S_{y} \ast I

Here Sx and Sy are the standard 3×3 Sobel kernels and I is one channel of the candidate RGB result. The gradient energy on the R−G colour-difference plane is:

E_{R-G} = \mathrm{mean}\!\left( G_{x}(R-G)^{2} + G_{y}(R-G)^{2} \right)

and symmetrically for B−G. The total score for a candidate pattern p is the sum:

S(p) = E_{R-G}(p) + E_{B-G}(p)

The winning pattern is the argmin over the four candidates:

p^{*} = \arg\min_{p \in \{\mathrm{RGGB},\mathrm{BGGR},\mathrm{GRBG},\mathrm{GBRG}\}}\ S(p)

The intuition: in natural images (astronomical scenes included), the R, G, and B channels are highly correlated at normal pixel scales — a star is bright in all three; a nebula edge appears in all three. A correctly-debayered image inherits this correlation, so the colour-difference planes R−G and B−G are smooth. An incorrectly-debayered image swaps or shifts colours against the real signal, which introduces zebra artefacts and chequerboard patterns that light up the colour-difference gradient energy. Minimising that energy picks the pattern that recovers the natural correlation.

The score is computed on the first time only; one of the four debayer passes is retained as the output, so there's no wasted work beyond the three losing passes. All four debayers run with cfa_drizzle=False through the standard Numba kernel.

12. Input normalisation

Debayer kernels expect float32 data in [0, 1]. The normaliser handles integer and float inputs separately:

Integer dtypes: scale by the dtype's native maximum.

a_{f} = a\ /\ M_{\mathrm{dtype}},\quad M_{\mathrm{dtype}} = \mathrm{iinfo}(\mathrm{dtype}).\mathrm{max}

So uint8 divides by 255, uint16 divides by 65535, etc.

Float dtypes: pass through unless the data looks like unnormalised 16-bit ADU values stored as float.

a_{f} = a\ /\ 65535\quad \mathrm{when}\quad \max(a) > 256
The threshold of 256, not 1, is deliberate. Flat-divided linear astronomical data legitimately runs to 2×–3× the full-scale value — a bright star that saturates would show up at an ADU of 65535, but after dividing by a flat frame with a central value of around 0.3, that becomes an output value of around 2.2. A float with max > 1.0 is not necessarily unnormalised 16-bit data — it might be perfectly valid linear astro data with a legitimate dynamic range above full scale. Crushing it by / 65535 would move the whole image into the range [0, 3.4e-5] and effectively flatten the signal below floating-point precision at the dark end. The 256 threshold catches genuine 16-bit float storage (where values commonly run to 50000+) while leaving flat-divided linear data alone.

The array is also ensured to be C-contiguous via np.ascontiguousarray before being handed to the Numba kernel, which assumes contiguous layout for its stride calculations.

13. Dialog threading model

The Bayer path runs the demosaic in a QThread worker (_DebayerWorker) so the UI stays responsive. The worker signals the dialog in three ways:

  • progress(int, str) — staged progress updates (5% on start, 96% on finalisation). Drives the progress bar and status label.
  • finished(np.ndarray, str) — the RGB result and the pattern that was actually used (for the step name on apply).
  • failed(str) — any exception's string representation. The dialog shows a critical message box and the status reads “Failed.”

The X-Trans path doesn't use the worker — rawpy is a C-extension call that holds the GIL for the duration of the decode, so running it in a QThread wouldn't improve responsiveness. The dialog shows a status message, calls rawpy synchronously, and reports completion.

14. Doc apply strategies and view refresh

The apply layer _apply_result_to_doc(dm, doc, rgb, step_name) always targets the specific doc passed to it, never “the active doc.” This is important for the headless and script paths, which may apply a debayer to a doc that isn't currently visible.

Preference order:

  1. doc.apply_edit(rgb, metadata, step_name=…) — preferred, participates in undo. Also tries the legacy two-arg and one-arg signatures as fallbacks.
  2. Direct mutation of doc.image and doc.metadata["is_mono"] = False, followed by an explicit refresh.

Refresh is done by _refresh_view_for_doc: it tries the doc manager's refresh_subwindow_for_document API first, falling back to walking the MDI subwindow list for one whose widget().document is identically the passed doc, calling that view's refresh_pixmap_from_document / refresh_view / update_from_doc hook if any exists, and finally calling plain update() on both the view widget and its subwindow. The active subwindow isn't changed; the user stays where they were.
