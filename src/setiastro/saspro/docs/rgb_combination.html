LRGB Combination

Build a single colour document from three mono channels, with an optional luminance channel — either from open views in the current session or from files on disk. Classical workflow for RGB/LRGB/narrowband assembly: process each filter's stack as mono (calibration, registration, denoise, stretch if you want pre-combine stretches) and bring them together here. Always creates a new document; nothing is written to the source channels.

1. Mode selector

Two radio buttons at the top of the dialog pick where the channels come from:

  • Use Open Views (default) — dropdowns list every open document in the session, and the channels are chosen from them. The quickest path when the mono masters are already loaded.
  • Load Individual Files — Load… buttons open a file picker (PNG, TIFF, FITS, XISF, JPEG) for each channel. Useful when you want to assemble a quick colour view without opening the mono masters as top-level documents first. This option is auto-disabled when SASpro's file loader isn't available in the current build.

Only one mode is active at a time — the inactive mode's widgets are greyed out so there's no ambiguity about which inputs will be used. The Luminance row in each mode is additionally greyed out until Add a Luminance (L) channel is ticked (§ 4).

2. Views mode

Four combo boxes — Luminance, Red, Green, Blue — each showing every open document by its window title. Luminance sits first so the rows read in the conventional LRGB order, but it is ignored entirely unless the L option is switched on.

Automatic channel guessing

When the dialog opens, SASpro scores every open document against each channel and pre-selects the best match. Scoring is two-layer, and the layers are summed:

Layer 1 — the FITS FILTER keyword. This is the definitive signal when it's present, because unlike a filename a FILTER card can't accidentally masquerade as something else. The keyword is read from a flat FILTER metadata key, or from a nested header under original_header, fits_header, header or wcs_header. Matching ignores case, spaces, underscores and hyphens.

A card that maps to a different channel scores roughly minus half its weight for the channel being considered, so a stack with FILTER = L is actively pushed out of the Red slot (−50) rather than being free to win it by default. OIII is deliberately not mapped, because observers split it to green or blue depending on the palette (HOO vs SHO) — it's left to the filename layer and your own choice.

Layer 2 — the filename. The fallback for files whose FILTER card is missing or non-standard. The full table is in § 6.3.

The best-scoring title is pre-selected; ties fall to the first match in dropdown order. If no title scores above zero for a channel, the first document is chosen as a neutral default and you're expected to pick manually. R/G/B are only auto-guessed when at least three documents are open; Luminance is guessed whenever there is anything to guess from. The heuristic is designed to Just Work on filenames like NGC7000_Ha.fits / NGC7000_OIII.fits / NGC7000_SII.fits or the more literal M31_red / M31_green / M31_blue, but it never locks a choice — the dropdowns are always user-overridable.

3. Files mode

Each Load… button opens an OS file dialog filtered to common astronomy formats. The chosen filename is shown next to its button; nothing is read from disk until Combine is pressed. Multi-channel files are supported — see § 6.1 for what happens to their channels, which differs between the colour channels and L.

4. Luminance (L)

Ticking Add a Luminance (L) channel enables the Luminance source row and runs the combined RGB through the same luminance-replacement pipeline as the standalone Recombine Luminance tool. The RGB keeps its colour; its brightness structure is replaced by L.

⚠ Do not combine a LINEAR L with LINEAR RGB.

Unless you have already matched the two stacks — total integration, sub-exposure length, pedestal/offset, filter throughput and camera response — the scale factor this tool applies is meaningless. You will get blown highlights or crushed shadows, and badly desaturated colour.

Normal workflow: combine RGB here without L, stretch it, stretch L separately, then use Recombine Luminance on the stretched pair.

4.1 Why linear LRGB goes wrong

Recombination computes the RGB image's own luminance Y and rescales every pixel by s = L / Y (the full maths is in § 6.5). That only works if L and Y sit on the same intensity scale. For stretched data they usually do, because stretching pushes both into roughly the display range. For linear data they almost never do:

  • Total integration — an L stack is often several times deeper than any single colour channel. More signal, higher mean level.
  • Sub-exposure length — different sub lengths scale per-pixel counts directly.
  • Filter throughput — an L or clear filter passes far more photons than any one of R, G or B over the same period.
  • Camera response — QE varies with wavelength, so identical photon flux yields different electron counts per channel.
  • Pedestal and offset — calibration pedestals differ between stacks. Near the background, s = L/Y is dominated by the difference in offsets rather than by any real signal.
  • Stacking normalisation — most integration routines rescale each stack to its own reference frame, destroying whatever cross-stack relationship survived calibration.
  • This dialog's own input normalisation — see § 6.2. Any channel whose values exceed 1.0 is divided by its own maximum, independently of the others. For integer-typed inputs that alone is enough to break the scale relationship between L and the colour channels, before any of the above is considered.

The result is that s is roughly a constant wrong number across the whole frame. Too high and the highlights blow and the colour washes out; too low and everything crushes. Either way chroma suffers, because colour lives in the ratios between R, G and B and those only survive when the overall scale is right.

The What this means… button in the dialog opens this same explanation in a scrollable window.

4.3 Linear-fit L to RGB luminance

Runs SASpro's standard Linear Fit engine before recombining: L is scaled so its median matches the median of the combined RGB's own luminance, measured with whichever luma profile is selected. This is the minimum pre-work for recombining linear data.

It handles the scale error — the first four causes in § 4.1. It does not handle the last three:

  • The fit is a pure multiply with no offset term, so a pedestal difference survives it. Subtract your pedestals before combining if the two stacks were calibrated differently.
  • No scalar fit can correct spectral response. An L filter sees a wider band than R, G or B, so even a perfectly fitted L carries structure the colour channels never recorded — which is what produces the flat, washed-out look often blamed on “too much L”.

Out-of-range handling is pinned to clip to [0, 1] rather than the Linear Fit dialog's own default of “normalize if needed”, because normalising subtracts the array minimum and rescales the whole frame, which would undo the median match that was the point of the fit.

If either median is at or below 1e-8 — a blank or near-black L, say — the fit is skipped rather than applied, because the engine's internal max(median, 1e-12) guard would otherwise yield an astronomical scale factor. The skip is recorded in the document metadata.

5. Combine

Reads the channels, verifies dimensions, stacks them into a new colour document, optionally applies the luminance, and opens a subwindow for it. The source documents and files are left untouched.

WCS inheritance

In views mode, the new document inherits a World Coordinate System from the first donor that carries one, in the order Green → Red → Blue. Green is tried first because it sits in the middle of the visible spectrum and is the usual astrometric calibration channel in LRGB rigs; the other two are tried only if green has no WCS. The luminance document is not a WCS donor — if only your L master is plate-solved, the combined document will carry no WCS and you should plate-solve it afterwards. In files mode no WCS is inherited at all, since the source documents don't exist in-session to pull headers from; open the files as documents first and use views mode if you want WCS on the result.

Shape requirement

All three colour channels must have identical dimensions, and L — when used — must match them too. A mismatched set raises a message dialog naming the mismatch and no new document is created; register or crop upstream and retry. L is not silently resampled here, because a luminance that doesn't line up with the colour data pixel-for-pixel will smear detail rather than sharpen it.

6. Technical details

Everything happens on float32 [0, 1]. The combine is a plain stack-along-axis-2; the interesting work is in the input normalisation, the channel-match scoring, and the optional luminance pipeline.

6.1 Mono extraction

The colour channels and the luminance channel are read differently, on purpose.

R, G and B pass through _mono_from_any, producing a 2-D float32 [0, 1] array:

  • 2-D input — passed through after normalisation (see 6.2).
  • 3-D input with any channel count ≥ 1 — the first channel is used; others are discarded. So if you accidentally point an R-channel selector at an already-RGB document, the dialog quietly uses its red plane rather than refusing — which is usually what you want for a quick recombine (“this already-combined RGB has the best red data; use its R plane with better G and B elsewhere”). For narrowband swapping, make sure the mono master is actually 2-D so there's no surprise.

L passes through _as_is_from_any, which normalises identically but keeps the channel count. A mono L is used directly; a colour L is run through compute_luminance with the selected luma profile, so pointing L at an RGB document extracts a proper weighted luminance rather than silently taking its red plane. This is also what makes the Max, Median and SNR profiles meaningful — with a mono L they only affect the weights used to measure the target's Y.

6.2 Normalisation

_to_f01 coerces every input to float32 [0, 1] without assumptions about where the data came from:

  • Integer dtypes are promoted to float32.
  • Floats are promoted to float32 if they aren't already.
  • If max(a) > 1 and finite, the array is divided by that max; otherwise the data is kept as-is. This means 16-bit integer data gets divided by its own max (not 65535), which keeps per-image contrast but drops a frame's absolute scale information.
  • Everything is finally clipped to [0, 1].
That per-image division is applied to each channel independently, including L. For colour combine it's harmless, since any downstream balance operation redoes per-channel scaling anyway. For luminance recombination it is not: it is one more reason the L/Y ratio is meaningless on linear integer data, and it happens inside this dialog regardless of what you did upstream. Float data already within [0, 1] is left alone and is unaffected.

Separator matching uses the character class [_\-\s\.] for “letter boundary”, so dots in filenames behave the same as underscores or hyphens. Note that a digit is not a boundary: this matters because SASpro's own gain prefix (…_G121_… on every master-light file) would otherwise false-match as a green channel on every file in the set, leaving them all tied and handing green to whichever happened to be first in the list.

The channel scorers run independently per title, and the title with the highest positive score wins its dropdown. Scores of zero or less leave the dropdown at index 0 as a neutral default — which is why, on a fresh session with generically-named documents, you'll sometimes see every channel defaulting to the first document; that's by design, not a bug.

6.4 Stack and clip

Once R, G, B are three identically-shaped 2-D float32 arrays:

RGB[y, x, 0] = R[y, x] RGB[y, x, 1] = G[y, x] RGB[y, x, 2] = B[y, x]

via np.stack([r, g, b], axis=2), then clipped once more to [0, 1] as a belt-and-braces guard against anything the per-channel normalisation might have missed in edge cases (NaN-dominated frames, etc.).

6.5 Luminance recombination

When L is enabled, the stacked RGB goes through this pipeline, in order:

  1. Saturation boost on the RGB (HSV), if non-zero.
  2. Chrominance NR on the result (Cb/Cr Gaussian blur), if non-zero. Both of these run before luminance is measured, so neither can skew the luma being placed.
  3. Build L — mono passes through; colour goes through compute_luminance with the selected profile.
  4. Linear fit of L onto Y, if enabled (§ 4.3).
  5. Recombine by per-pixel scaling.

The recombination itself lifts both images by the pedestal p and compresses by (1 + p), scales, then inverts the lift:

Y = wR·R + wG·G + wB·B s = L / (Y + eps) RGB' = RGB · s

With a soft knee k, s is replaced by s / (1 + k(s − 1)) before it is applied. With a blend β below 1, the output is RGB·(1−β) + RGB'·β. The transform is an identity when L equals the image's own Y, which is the round-trip guarantee the whole approach rests on.

The weight vector w comes from the selected profile. Sensor profiles supply their own measured weights. Equal uses (⅓, ⅓, ⅓). Rec.601 and Rec.2020 use their standard vectors. Max, Median and SNR have no weight vector of their own, so they fall back to Rec.709 for measuring Y — they only change how L is extracted when the L source is a colour image.

6.6 Document creation and WCS transfer

The result is handed to the document manager via whichever of open_array, open_numpy or create_document is available, with the metadata described in § 6.7 and the title derived from the mode (as in § 5). The main window's WCS helpers (_extract_wcs_dict, _apply_wcs_dict_to_doc) are then called in the G → R → B donor order until one yields a usable WCS, which is copied onto the new document before its subwindow is spawned. If no donor has a WCS, the new document carries none — a plate-solve can be run on it afterwards from any of SASpro's astrometry tools.
