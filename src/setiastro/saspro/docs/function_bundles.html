Function Bundles

A reusable, ordered sequence of SASpro commands — each with its own preset — that can be applied in one gesture to the active view, fanned out across every view in a View Bundle, or packed into a chip on the shortcut canvas. Bundles are built by dragging shortcut tiles into the dialog; each tile dropped becomes a step. The dialog remembers your bundles between sessions and persists the chip layout on the canvas across restarts.

Workflow
Open Function Bundles. Create a bundle (New) and give it a name (F2 or double-click to rename). Drop shortcut tiles from the canvas onto the Steps list — each drop appends a step with that command's current preset. Reorder with the arrow buttons or by dragging within the list; edit a preset by double-clicking a step or using the Edit Preset button. Apply to Active View runs the whole bundle on the focused doc; Apply to View Bundle… fans it out across every view (and every file path) in a saved view bundle. Compress to Chip drops a purple chip on the shortcut canvas — drag it onto any view to apply, or Alt-drag it elsewhere to pass the bundle as a drop payload.

The signature behaviour of this tool is synchronous step chaining across asynchronous SASpro commands. Many SASpro tools (Statistical Stretch, GraXpert, Cosmic Clarity, RC-Astro, etc.) return from their drop handler immediately and continue processing in a background worker — so a naive sequence would run step N+1 against step N's unmodified image. The bundle runner solves this by arming a document-change watcher before every step, then blocking the next step until the document reports a change (either via its changed signal or via a bumped edit counter), with a special indefinite wait when Cosmic Clarity's headless flag is set. The result is a reliable, order-preserving pipeline that respects each tool's real completion.

1. The bundle concept

A Function Bundle is a named, ordered list of steps. Each step is a dictionary with at least a command_id (the id of a SASpro command, e.g. stretch_statistical, graxpert_bg, cosmic_clarity_sharpen) and an optional preset dictionary carrying that command's parameters. Steps are shaped exactly like the payloads a shortcut tile drops onto a view, which is why building a bundle is literally “dragging shortcut tiles into a list.”

A single SASpro session can hold any number of bundles, each with its own name. Bundle data lives in QSettings under the key functionbundles/v1 as a JSON array, so bundles survive restart and can be included in .sass shortcut-export files for sharing.

step = { "command_id": "stretch_statistical", "preset": { "target_median": 0.25, "linked": false }, } bundle = { "name": "Linear → Stretched", "steps": [ step_1, step_2, … ], }

The two panes of the dialog mirror this: the left pane lists bundles, the right pane shows the steps of the currently selected bundle. Everything you can do to a bundle (new, duplicate, delete, rename) is on the left; everything you can do to its steps (reorder, remove, clear, edit preset) is on the right.

2. Building a bundle

Three ways to add steps to the currently selected bundle:

  • Drop a shortcut tile from the shortcut canvas onto the Steps list or the dialog background. The tile's command id and current preset are appended as a step.
  • Drop another function bundle onto the Steps list. The nested bundle is expanded in place — its steps are appended one by one, not stored as an opaque reference. If you later edit the source bundle, this bundle's copy of those steps won't change.
  • Internal reorder: once steps are in the list, drag within the list to reorder them. The list is set to InternalMove mode so you can't drop arbitrary items from outside Qt, only reorder existing ones.
Dragging a shortcut tile captures the preset at the moment of the drop. If you later change that tile's preset on the canvas, the bundle still runs with the preset you dropped. Rebuild the step (remove and redrop) if you want the new preset, or edit the step's preset in place with the preset editor.

A newly created bundle gets a placeholder name like “Function Bundle 3”; rename it with F2 or by double-clicking the entry. Duplicates get a “ (copy)” suffix. The badge on the chip (if any) updates automatically to reflect the current step count.

3. Editing steps

Each step shows as a row command_id — preset_label. The preset label is derived automatically: if the preset has a name or label field, that string is shown; otherwise a compact summary of its first three keys ({k1, k2, k3…}) is used. Hover a row to see the full line as a tooltip (useful when the row elides).

Available step actions:

  • Move Up / Move Down buttons — reorder the selected rows (works with multi-select).
  • Remove Selected — deletes the selected rows.
  • Clear Steps — empties the whole bundle (keeps the bundle, drops all its steps).
  • Edit Preset… — opens the preset editor for the currently selected single row (enabled only when exactly one row is selected).
  • Context menu (right-click a step): Edit Preset, Clear Preset, Duplicate Step, Remove Step.
Shortcuts in the Steps list
Delete / Backspace — remove the selected rows.
Ctrl+A — select every step.
Return / Enter — open the preset editor on the selected step.
Ctrl+drag within the list — reorder (standard Qt internal-move DnD).

Shortcuts in the Bundle list
F2 — rename the current bundle.
Right-click a bundle → Rename…

4. The preset editor

When you edit a step's preset, SASpro tries the step command's bespoke preset editor first — the same editor you'd see if you right-clicked that command's shortcut tile and chose “Edit Preset…”. These editors know what parameters the command accepts, their ranges, their units, and their validation rules. Not every command has a bespoke editor (particularly third-party plug-ins); for those, the editor falls back to a plain JSON text editor.

Fallback behaviour matters: if a bespoke editor exists and the user cancels it, nothing changes — the fallback JSON editor is NOT opened. Cancelling a rich UI means “I don't want to change this preset,” not “show me the raw JSON instead.” The JSON editor only appears when the command has no bespoke editor at all.

The JSON editor is a plain multiline text box seeded with the current preset in indented JSON. On OK, the text is parsed; if parsing fails, the error is shown and nothing changes. An empty text box commits a None preset (equivalent to clearing it).

5. Running a bundle

Three apply targets at the bottom of the right pane:

  • Apply to Active View — runs the bundle on whichever MDI subwindow is currently focused. If no view is active, the button reports the condition and does nothing.
  • Apply to View Bundle… — opens a picker listing every saved View Bundle. Pick one and the function bundle fans out across every view in it, step by step, sequentially. (See the View Bundles doc for the file-path path — a View Bundle can carry disk files too.)
  • Compress to Chip — see §6.

During a run, each step logs its index, command id, payload, and completion reason (signal, count, signal_sync, count_sync, timeout, or noop) via the main window's _log hook plus stdout. Cosmic Clarity steps get their own >>> BEGIN CC / <<< END CC markers so they're easy to spot in long logs.

An error raised by a single step does not stop the bundle. The error is captured, the next step runs anyway, and all errors are summarised in a single message box at the end. This is deliberate — a bundle run against twenty views shouldn't abort because one view hit a transient issue — but it means you should check the log and the status label after a run completes.

6. The function-bundle chip

Compress to Chip spawns a small purple widget — the function-bundle chip — on SASpro's shortcut canvas. The chip stays live for the whole session (and re-appears next launch); the dialog itself can be closed without destroying the chip.

Chip behaviours:

  • Drop a shortcut tile on the chip → append that step to the bundle (same semantics as dropping into the dialog). A function bundle dropped onto a chip is expanded step-by-step into the bundle, same as in the dialog.
  • Alt+drag the chip → starts an external drag with the bundle as a function_bundle payload ({"command_id": "function_bundle", "steps": […], "inherit_target": true}). Drop it on a view, a view bundle chip, or any other drop target that handles bundle payloads.
  • Left-drag the chip → move it within the canvas; position is clamped to the canvas bounds and saved on release.
  • Double-click the chip → reopen the Function Bundles dialog and focus this bundle.
  • Right-click the chip → context menu with Delete Chip (removes the chip only; the bundle itself stays).
  • Delete / Backspace while the chip is focused → same as context-menu Delete Chip.

The number badge on the chip shows the current step count and recolours (purple when the bundle has steps, grey when it's empty). The chip's title tracks the bundle's name; rename the bundle and the chip updates automatically.

Multiple chips can live on the canvas at once (one per bundle). On launch they're placed in a staggered row near the upper-right so view-bundle chips (which land upper-centre) don't collide with them.

7. Progress and step status

Below the Steps list sits a status label and progress bar. During a run:

  • The status label reads “Running step N/total: command_id — preset_label”, so you can see which step is executing.
  • The progress bar advances per step (0% at start, N/total × 100% as each step completes).
  • When a sub-step runs indefinitely (Cosmic Clarity sub-workflow, long external worker), the progress bar switches to indeterminate (marquee) mode and the status label describes what's being waited on.
  • A busy cursor is set for the duration of the run and restored on completion or error.
  • On completion the label reads “Done.” and the bar snaps to 100%; errors (if any) are summarised in a dialog.

If you run the bundle against a View Bundle, the status covers one view at a time — so you see progress through step N/total for view 1, then view 2, and so on.

8. Script-level entry point

Function Bundles also integrates with SASpro's command/script system via the CommandSpec id function_bundle. Scripts can call it two ways:

  • By name: pass a saved bundle's name as preset["bundle_name"] and the runner looks it up in the same QSettings store the dialog uses.
  • Inline: pass preset["steps"] as a list of step dicts directly. Legacy keys cid and id are accepted as aliases for command_id, so bundles exported from older SASpro versions still run.

Optional preset keys:

  • inherit_target (default True) — if true, every step runs against the same target; if false, each step is dispatched on its own and can retarget.
  • targets — either "all_open" or an explicit list of doc pointers. When present, the bundle fans out exactly as the UI path does; target_sw is set to None and the main-window drop handler does the dispatch.

The runner does not step through ctx.run_command itself; it synthesises a single function_bundle payload and hands it to MainWindow._handle_command_drop, which is the same path a UI drop takes. This keeps script execution and UI execution bit-for-bit identical.

9. Technical details

Internal mechanisms numbered continuing from the usage sections.

10. Payload shape and normalisation

The internal step payload accepted by _handle_command_drop looks like:

{ "command_id": "stretch_statistical", # required "preset": { … }, # optional, per-command schema "on_base": true, # optional, apply to base layer only "label": "First stretch", # optional, for logging … # any extra keys pass through }

Bundles saved from older SASpro versions sometimes stored the command id under cid or id instead of command_id. The script runner's _normalize_steps_for_hcd accepts all three (in order of preference) and rewrites each step into the canonical shape before dispatch. Unknown extra keys pass through unchanged, so new per-command fields don't break old bundles.

11. Doc-change wait mechanism

The core of the sequential runner. For each step, the runner follows the arm → run → wait cycle:

# 1) ARM — before the step runs handle = arm_doc_change_watcher(sw) # captures: doc, edit_count_0, connects 'changed' signal # 2) RUN — synchronous call into main-window dispatcher mw._handle_command_drop(step, target_sw=sw) # 3) WAIT — until one of these is true: # a) the 'changed' signal has fired, OR # b) edit_count(doc) > edit_count_0, OR # c) elapsed >= timeout_ms AND Cosmic Clarity is NOT running reason = wait_for_doc_change(mw, sw, cid, handle, timeout_ms=120_000)

Arming before running is essential. Many SASpro tools apply synchronously inside their drop handler and emit changed before the dispatcher returns — if the watcher connected after the dispatch, that fire would be missed and the wait would time out even though the step had completed. The watcher connects first, the dispatch happens, and any synchronous signal reaches the listener.

The edit counter is a resilience hedge: not every doc class in SASpro's history has emitted changed consistently. The waiter looks for a counter on each of these attribute names in order: edit_count, _edit_count, revision, _revision, version; failing all of those, it falls back to len(history) / len(_history) / len(undo_stack). Callables are invoked. If none of them exist, the counter check is skipped and the wait depends on the signal alone.

The wait loop pumps Qt events every 25 ms with a sleep in between, so the UI stays responsive — the progress bar updates, status label refreshes, and buttons stay clickable (though their actions queue until the wait returns). On timeout, the wait returns timeout as the completion reason and the runner moves on; the per-step error list stays empty unless the dispatch itself raised.

12. No-op exemptions

Some steps intentionally don't modify the image — saves, exports, viewers, inspectors. Waiting for a document change after one of these would always hit timeout. The waiter maintains an explicit no-op set:

_NOOP_CIDS = { "checkpoint_save", "save_project", "save_active", "save_active_as", "export_fits", "export_fits_bundle", "plate_solve", # writes header, may or may not emit 'changed' "psf_viewer", "image_peeker", }

For any step whose command_id is in this set, the wait is skipped entirely and the runner moves immediately to the next step. plate_solve is in this set because it writes WCS cards into the header without necessarily emitting changed — keeping it here means plate solving in the middle of a bundle doesn't stall for two minutes before timing out.

13. Cosmic Clarity wait

Cosmic Clarity is SASpro's AI noise reduction and sharpening tool; it runs as a separate headless process and can take minutes on large images. The bundle runner knows about it specifically.

While a Cosmic Clarity run is in progress, two flags indicate it:

  • mw._cosmicclarity_headless_running on the main window (set at process launch, cleared on exit).
  • cc/headless_in_progress in QSettings (same lifecycle, visible across process boundaries).

If either is true during the per-step wait loop, the 120 second timeout is bypassed — the loop keeps polling as long as CC is running, up to an upper bound of two hours. After CC's flag clears, a secondary _wait_for_cosmicclarity pass runs to make sure the subprocess has fully exited before the next step begins. This two-stage guard means a long CC call followed by Statistical Stretch never races the stretch against a mid-flight CC write.

14. Chip persistence

Chip positions are saved to QSettings under functionbundles/chips_v1 as a JSON array of { "index": …, "x": …, "y": … } records. Writes happen on every chip-drag release and on bundle delete, so the layout is always current.

Restore runs at dialog construction time: for each saved record, the matching bundle is looked up by index (chips bind to bundle positions, so reordering the bundle list without reassigning chips can produce stale bindings — this is why bundle delete explicitly removes the chip for that index). A missing or out-of-range index silently skips. If the shortcut canvas isn't available yet (startup race), the restore is a no-op — it'll run again the next time the dialog is opened.

Chip restore at app startup is driven by restore_function_bundle_chips(parent), which constructs the dialog singleton with auto_spawn_only=True — the dialog itself stays hidden, but its chips land on the canvas as if the dialog had just been opened.

15. Preset editor dispatch

Bespoke preset editors live under setiastro.saspro.shortcuts and are discovered via two lazy imports: _has_preset_editor_for_command(cid) checks whether an editor exists; _open_preset_editor_for_command(parent, cid, preset) opens it. The import is lazy so the Function Bundles module stays independent of the shortcuts module's own circular-import constraints.

If the shortcuts module fails to import or has no editor for the step's command id, the JSON editor fallback runs directly in _edit_preset_dialog — it's a plain QPlainTextEdit seeded with json.dumps(current, indent=2) and accepted only when the content parses as valid JSON.

16. Import / export in .sass files

Function bundles ride along with SASpro's shortcut-export files (.sass). The export side is export_function_bundles_payload(), which reads both the bundle definitions and the chip layout from QSettings and returns them as a { "bundles": […], "chips": […] } dict.

The import side is import_function_bundles_payload(payload, parent, replace_existing=False):

  • With replace_existing=True the current bundles and chip layout are overwritten.
  • With replace_existing=False (default) new bundles are appended, and chip indices in the imported payload are offset by the current bundle count so each chip still points to its own bundle after the merge.

After the import, any live dialog is refreshed via reload_from_settings_after_import(); if no dialog exists, chip restore runs so the imported chips land immediately on the canvas.
